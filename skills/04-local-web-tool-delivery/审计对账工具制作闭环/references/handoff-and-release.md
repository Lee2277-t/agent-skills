# 交接稿与发布：把方法固化成可接手的资产

十几轮之后，真正的瓶颈不是写代码，而是「下一个人（或下一个会话）能不能不重新逆向就改对」。本项目的答案是：维护一份不进交付包的 `AGENTS.md`，以及一套固定的发布清单。

## 一、交接稿的结构（按这个顺序写）

```text
1 项目定位与硬约束    数据不出本机 / 用户是谁 / 交付形态 / 浏览器支持
2 文件清单            每个文件干什么、哪些不进包
3 运行与打包          启动命令、打包命令、升版本要改哪几处
4 架构与数据流        单一 state 的字段表、两条主链路、渲染层入口
5 核心口径规则        编号 §5.1…§5.N，每条写清「是什么/为什么/改它要跑哪套测试」
6 UI 约定             文案语气、颜色 token、各区块入口、打印媒体名单
7 导出工作簿结构      每张表的列、条件性写入、行号偏移（改一处要连改几处）
8 测试与验收          每条命令、期望数字、夹具清单与期望值
9 已知坑              都是真踩过的，写现象 → 根因 → 正确写法
10 未做 / 候选需求    已做、已判定不做（附理由）、当前限制
11 开源借鉴与许可证台账
```

**编号比行号长寿。** 引用代码一律写「函数名（:行号）」，行号只作辅助；文档里反复出现「行号会漂，按名检索」这句警告。任何一次大改之后，行号几乎必然过期，但函数名与口径编号仍然可 grep。

## 二、文档维护纪律（比写文档更重要）

1. **每条口径一个编号**，测试里引用编号（「本套件守 §5.38」），改口径时两边一起改。
2. **改完立刻 grep 复核**：并行改同一文件时，`Edit` 可能返回成功但内容没落盘。落一条验一条，不要攒一批再验。
3. **锚定代码文本，不锚定行号**：编辑时用周围代码作上下文，不用「第 1234 行」。
4. **文档里的数字标版本和日期**（本项目：v2026.11.06-r2，19 套件 / 849 断言 / 27 项黄金 / 25 个夹具 / 包 490,584 字节）；下一轮先跑一遍再改数字，不沿用上一轮的估值。
5. **失败实验也要留档**：把「为什么这个方案被推翻」写进 §9，比只写正确做法更能防止复发。
6. **文档不进交付包**：交接稿、测试目录、差距清单、重构笔记都在打包白名单之外。

## 三、发布清单（按顺序，每步可回退）

1. **升版本，三处同步**：
   - `version.txt`（服务注入用）；
   - `app.js` 顶部 `APP_VERSION_FALLBACK`（`file://` 兜底）；
   - `更新说明.txt`（给用户看的变化，口语、说清「没改什么」）。
   两处版本号不一致会表现为「http 与 file:// 下页脚版本不同」。**启动服务会把版本读进内存**，改完必须重启服务才看得到。
2. **语法**：`--check` 通过。
3. **全量回归**：`run-all` 末行 `PASS`，断言数不少于上一轮；黄金 `N 项全部通过`。
4. **真窗口**：动过指针/打印/布局/剪贴板就重跑对应 QA，报告里 `errors:0`。
5. **真实语料**：动过认列/勾选规则就重跑，记录 `files/sheets/usable/sus/noAmount/errors`；**不要拿「自动勾选数」当指标**（默认零勾选后恒为 0）。
6. **重打包**：白名单脚本逐条 `assert size>0`，再回读 CRC、条目列表、逐文件字节；独立校验脚本列条目名 + `testzip()` + 解压后逐文件 MD5。
7. **确认包内容**：交付目录里不该出现的文件（交接稿、测试、真实底稿）不在条目列表里。
8. **交给用户亲测**：发版闸门的最后一条，见 `benchmark-and-convergence.md` 第六节。

## 四、打包白名单的写法

```python
items = ['index.html', 'assets/app.js', 'assets/styles.css', 'assets/favicon.svg',
         'vendor/xlsx.full.min.js', '打开对账工具.bat', 'serve.ps1',
         'version.txt', '更新说明.txt', '第三方许可.txt']
for name in items:
    assert (root / name).stat().st_size > 0, name
    archive.write(root / name, name)
assert archive.namelist() == items
assert archive.testzip() is None
for name in items:
    assert archive.read(name) == (root / name).read_bytes(), name
```

- **必须用白名单**，不要用「目录下所有文件再排除」：排除规则会漏，白名单漏了会立刻 assert 失败。
- 新增交付文件必须同时改 `items`，否则包静默缺文件。
- 覆盖用户正在用的旧 zip 前，先记录旧包大小与时间并确认——那是用户手里的成品。

## 五、面向用户的那份「更新说明」怎么写

- 先说**这一版改了什么、对用户意味着什么**，再说细节；
- 每条变化都补一句「没改什么」（如「这些都不改动任何金额」）；
- 出现新入口的，写清「在哪里、点了会怎么样」；
- 不出现「解析、映射、字段、序列化、容差算法」这类词；
- 错误与新限制写「怎么办」，不写「报什么错」。

## 六、收尾汇报（用户格式）

```text
现有功能：这一轮做完后，用户打开就能用的能力（按操作顺序说）。
未完成事项：没做的、以「用户亲测」为闸门的、已知限制。
直接打开的网址：http://127.0.0.1:<端口>/index.html（端口从启动器 marker 读）。
```

不要用「已完成」代替「已验证」；不要把「测试全绿」说成「可以发版」——发版闸门在用户手里。
