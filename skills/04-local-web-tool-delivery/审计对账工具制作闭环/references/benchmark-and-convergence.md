# 对标迭代与收敛：十几轮之后怎么不失控

长周期工具项目最难的不是第一版，而是第 10～18 轮之后仍然「知道自己在做什么、为什么停」。本项目用一套固定节奏跑到收敛，方法可以直接照搬。

## 一、对标选型：每个工具承担一种角色

不要泛泛「参考几个软件」，按角色选，每个角色只拿它最擅长的那一点：

| 角色 | 拿什么 | 注意 |
|---|---|---|
| 结构正确性标准 | 「什么算对、什么算错、错到哪种程度」的语义 | 通常是同类里最严的那个项目 |
| 算法/交互标杆 | 具体算法思路或交互（如分面筛选、先强后弱匹配） | 只借语义，不借源码 |
| 独立裁判 | 用另一个实现验证产物 | 裁判代码一行都不进项目 |
| 产品形态参考 | 面向同类用户的界面与文案 | 只看产品，不看实现 |
| 差距清单来源 | 功能表逐条对照 | 只对标功能，不看代码 |

**先查许可证再决定能不能读代码**：MIT/BSD/Apache 可读可用（仍要登记）；GPL/AGPL **只读文档与公开行为**，不读源码、不贴代码。许可证结论写进交接稿台账（对象 / 许可证 / 用在哪 / 是否复制代码）。

## 二、差距表是唯一的待办清单

格式固定，状态只有三种词：

```text
# | 差距 | 严重度 | 影响范围 | 价值×成本 | 状态
G1 | …… | 高 | 全部导出 | 低×中 | ✅ 已收敛
G6 | 汇率折算合计 | — | 合计口径 | 高×高 | 🚫 已知取舍
```

- `✅ 已收敛` / `🚫 已知取舍` / `⏳ 推迟`，不许出现第四种状态。
- 每收敛一条，同步更新差异说明与测试条目；「已收敛」必须有断言背书，不能只是代码写了。
- 判「不做」的必须写理由与替代方案（见 `caliber-red-lines.md` 第六节）。

## 三、一轮的固定五段

1. **选**：从差距表挑一条，写价值×成本；高价值低成本先做。一轮只做一条主差距，附带修复可以，但不能塞第二条新功能。
2. **借**：读对标的公开行为/文档，借语义；借不到的（AGPL）只描述「它怎么做」，代码自己写。
3. **落**：四层依次落地——核心计算（纯函数、可被测试直接调）→ 数据/导出结构 → 界面（含「怎么办」文案）→ 测试（夹具 + 断言 + 只读性）。
4. **证**：全量回归 + 真窗口（若动了交互/打印）+ 真实语料（若动了认列）+ 重打包。
5. **报**：固定四段，缺一段算没交付：

```text
改动点：改了哪些文件、哪个行为。
借鉴来源：对标了谁、借的是语义还是代码（没借写「无」）。
验证结果：命令 → 实测数字（19/19 套件、849 条断言、包体字节）。
残留问题：没做到的、明确拒绝的、下次要接的。
```

## 四、真实缺陷优先于新功能

每轮对标都应该顺手做一次「自己的产品在当前状态下会不会骗人」的自查。本项目第 18 轮就是靠这个抓到真缺陷：三档筛选和搜索在打印媒体里被隐藏，纸上只画筛出来的企业，却没有任何痕迹——看着像完整底稿。修复是给打印戳加一句「本页只列筛出来的 N 家（一共 M 家，原因…）；要全部打出来就……」并补一组打印断言。

规则：**自查发现的「会误导用户」的缺陷，优先级高于差距表里的新功能**；修完必须补一条能复现它的断言，否则下一轮会复发。

## 五、什么时候停

停的条件是**差距表里只剩「已知取舍」与「推迟」**，不是「做累了」或「看起来够了」。停之后：

- 差距表顶部写「本轮后冻结，之后只允许更正事实」；
- 新需求另开决策记录并写明「为什么解冻」，不在已冻结轮次里偷偷插队；
- 转入收尾：重跑基线、同步交接稿、升版本、重打包、交给用户亲测。

## 六、发布闸门的最后一条是「用户自己走一遍」

自动化能证明「算得对、点得动」，不能证明「非技术用户真的会用」。本项目的发版条件写死为：**用户本人拿一份真实底稿从头走到尾**（导入 → 勾表 → 认列 → 对账 → 看复核提示 → 导出/打印），期间不出需要人猜的提示。在此之前只报「改完待发」，不报「可以发布」。

## 七、轮次纪律（防止第 N 轮把前面推翻）

- 每轮开始先读交接稿里对应的口径编号，确认这次改的是哪一条，改完更新该条；不要凭记忆改。
- 任何「默认值」变化都算口径变化：本项目第 19 轮把「导入后自动勾选可用的表」改成「一张都不勾」，同时要改代码、测试期望、界面文案、更新说明与交接稿五处。
- 旧结论可以被推翻，但必须留下「为什么推翻」的痕迹（本项目在交接稿里保留「自动勾选 19→64」的失败实验，防止后人再试一遍）。
