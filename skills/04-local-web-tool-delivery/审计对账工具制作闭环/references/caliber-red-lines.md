# 口径红线：先定「什么不许动」，再写功能

金额类工具最大的风险不是算错，而是**悄悄算错**：一个提示功能顺手改了金额、一个「辅助视图」进了合计、一个筛选让导出少了几家，事后没有任何痕迹。本项目（双边对账）把这件事做成了制度：每条功能先归类，再决定它能碰什么。

## 一、三个提问定一条口径

对每个新功能，先回答这三句，答案写进交接稿（本项目是 `AGENTS.md` 的编号条目）：

1. **它会不会改变任何金额？** 会 → 这是主链路，必须重跑全部金额类回归，并在导出说明里写清口径变化。
2. **用户看不见它时，谁负责说？** 不存在「用户自己会发现」的功能。凡是缩小了显示范围、跳过了数据、没认出列、算出了 0 笔，都必须有一处**主动说明**。
3. **它能被撤销吗？** 只改显示/标记的，要有撤销或恢复入口；改金额的，默认不做（见「已判定不做」）。

## 二、红线矩阵（本项目的实例）

| 功能 | 允许碰什么 | 绝不许碰 | 留痕位置 |
|---|---|---|---|
| 自动核销配对 | `pairing.decision`（采纳/不采纳） | 两笔金额、方向、净额 | 配对区 + 导出「核销配对」表 |
| 日期就近匹配 | 配对**对象**与顺序、>90 天提醒 | 金额、是否配对 | 配对行 + 导出「日期情况」列 |
| 同单据号 / 摘要线索 | 提示文字 | 并入 `pairings`、改金额 | 配对区提示块 + 条件性导出表 |
| 账龄分档 | `ageBand`、分档统计、档位设置 | 笔数、金额、配对 | 明细标记 + 「账龄分析」表 |
| 「差一点就能配上」 | 配对**余料**的列表 | 写回 `pairings`、改容差、改金额 | 汇总条 + 配对块 + 「差一点」表 |
| 结果页三档筛选 | 屏幕上画哪几家、导出范围标签 | `groups`、任何 `cents`、结果指纹 | 筛选条 + 导出「对账说明」+ 打印戳 |
| 数据源列表分批 | DOM 里画几行 | 勾选状态、参与对账的表集合 | 列表尾部「还有 N 张」 |
| 底稿快照比对 | 只读两份 JSON，产出变化清单 | 当前结果、采纳状态、说明文本 | 比对卡 + 「底稿比对」工作簿 |
| 导出校验码 / 归档包 | 文件的 SHA-256、字节 | 工作簿内容、任何 state | 校验码卡 + 归档 zip |
| 打印 | 打印媒体的显示 | 屏幕状态、数据 | 打印戳自证筛选子集 |

矩阵的要害是**每一行都有「绝不许碰」**。没有这一列，功能边界就靠记忆，而记忆会在第 10 轮之后失效。

## 三、提示型功能的实现契约

新增一个「只是提示」的功能时，照这五条做，缺一条就会被后续维护者误接进主链路：

1. **新建字段，不复用金额字段**。本项目用 `group.nearMiss[]`、`state.dimensionWarnings[]` 这类独立数组，绝不往 `pairings` 或 `rows` 里塞。
2. **在主链路跑完之后计算**，并且只吃主链路剩下的东西（「差一点」只吃 `leftoverRecv/leftoverPay`），这样天然满足「一条记录只被一个结论消费」。
3. **明确它进不进结果指纹**。本项目的规则：只影响「呈现/提示」的不进指纹（`nearMiss`、三档筛选、差异说明、签字信息），影响「对账结论」的进（容差、比例、账龄基准日、采纳状态）。写进交接稿，不要两头改。
4. **测试里放一条只读断言**：功能开启/切换/导出前后，逐企业 `recvCents/payCents/netCents`、逐笔 `cents`、`buildResultFingerprint(state.groups)` 必须逐项相同。本项目 `near-miss-check`、`facet-filter-check` 都守着这一条。
5. **界面文案自己声明边界**：「只是提示，不改变净额」「只是给个参照，不改任何金额」——不是免责口号，是给用户判断依据。

## 四、金额域的基础口径（换项目也要先定）

- **整数分**：所有金额以「分」整数计算与比较，展示时才除 100 保留两位；禁止浮点累加。
- **原表值 vs 解析值分开存**：`cellCents` 是格子里写的数（取数核对吃它），`cents` 是归一后的口径；红字/负数翻转不得污染 `cellCents`。
- **负数不是减项，是方向**：`amount < 0` ⇒ 取绝对值并把方向翻到对立侧（应收↔应付）；`-0` 不翻转。
- **方向有优先级**：显式方向列 > 用户整表指定 > 表名 > 标题行 > 文件名；两侧特征词同时命中就不猜。
- **净额 ≠ 会计抵销**：净额只用于排差异与准备函证，界面上必须有这句话，导出「对账说明」也要有。
- **不同币种不做汇率换算**：分桶合计、原数相加，能加总的只有同一币种。想加「折算为本位币」就必须引入外部汇率，直接判为违背离线约束。
- **控制总数恒等式**：`原表金额 = 纳入 + 跳过 + 范围外 + 未归类`，格数同理，差额必须为 0；这不是对账结论，是「算全了没有」的证据。

## 五、把「不确定」写到屏幕上

本项目的诚实清单，可直接照搬：

- 列是猜的 → 行上标「按内容认出来的，可能要人工核对」，并写明认的是哪一列、什么表头。
- 表可用但勾选后 0 笔 → 列表徽章 + 数据检查 + 预警 toast + 导出说明**四处点名**，并提示「取消勾选」。
- 只算表头下一段 → 写明「只算第 X～Y 行（范围外还有 N 行）」，并给「整张都用」的入口。
- 空值不当 0 → 账龄没写的单列一档、币种没写的单列一组，绝不塞进第一个桶。
- 筛过再打印 → 打印戳强制写「本页只列筛出来的 N 家 + 怎么打全」。
- 出错了 → 文案先讲「怎么办」（去只留要核对的那几张表另存），再讲现象，不出现内部术语。

## 六、「已判定不做」也要写

红线类决策必须落纸，否则下一轮会有人重新提：

```text
不做：把不同币种折算成本位币合计。
理由：折算需要外部汇率源，违反「数据不出本机」；且会引入不可复现的中间值。
替代：按币种分桶、原数相加，界面声明不做汇率。
```

本项目已登记的「不做」：按配对结果自动改账（部分核销过账）、把校验码写进导出工作簿内部（会改变字节，破坏「下载文件 = 卡片校验码」的自洽链）、引入汇率折算、给归档 zip 本身算校验码（循环依赖）。
