# 收尾与交接

收敛之后的工作不是「再加点功能」，而是把代码变小、把重复收口、把状态写清楚。顺序很重要：**先保命，再拆；能用测试证明的才动，不能证明的先记录。**

## 1. 先建安全网

1. **版本控制**：项目若不在 git 下，先 `git init` + 一次基线提交，`.gitignore` 掉运行时（Electron runtime）、测试产物、`__pycache__`。不想建库就整目录复制成 `<项目名>_backup_<日期>/`。
2. **基线数字**：全量回归条数与耗时、命令行断言数、单文件字节数、差距表状态分布。
3. **基线哈希**：对每个源码文件取 sha256，写进交接文档。它的用途只有一个——重构后证明「没动的地方真的没动」。
4. **先跑绿的基线**：在本来就红的基线上重构，等于同时改两件事，事后无法归因。

```bash
sha256sum web/js/*.js web/index.html build_single.py desktop/cli.cjs
```

## 2. 重构顺序（按价值×风险）

| 优先级 | 做什么 | 风险 | 判断 |
|---|---|---|---|
| P0 | 快照 + 基线 + 跑一次全绿 | 无 | 必做 |
| P1 | 消除重复实现与口径分歧（两个 sanitize、两份错误文案、重复的报告行拼装） | 低 | 优先做，收益最高 |
| P2 | 拆超大引擎文件：只抽纯函数到新文件，方法名与签名不变 | 中 | 准备长期维护才做 |
| P3 | 拆界面文件：先移纯函数，再按面板拆事件绑定 | 中高 | 收益有限，可不做 |
| P4 | 测试与夹具整理：CASES 补全、加 `--fast` 预设、清理可重建的产物 | 低 | 建议做 |
| P5 | 构建与交付复核：重建、双形态各测一次 | 低 | 必做 |
| P6 | 文档收尾：冻结声明、数字对齐 | 低 | 必做 |

**P1 的正确做法**：不要直接删「看起来重复」的那一份。先写一个对比脚本，把同一批输入分别喂给两版实现，证明差异只落在测试没覆盖的输入上，再决定统一到哪一版、补哪些用例。本项目两个 `sanitize` 的控制字符、空白折叠、前导点、长度上限规则都不同，产物文件名是对外契约，删错一个就改变用户看到的文件名。

**P2 的正确做法**：

1. 只抽**纯函数**（字节转换、字典读取、文件名清洗、数值/矩阵解析）→ 新文件 → 挂 `PT._util` → 原文件用局部别名接回。
2. 新文件必须同时加进 `index.html` 和 CLI 的 eval 列表，且顶层不碰 DOM。
3. `module.exports` 只保留在最后一个文件。
4. 每抽一块就跑：对应探针 + 引擎用例 + 命令行断言。抽完一块再抽下一块，不要一次性大搬家。

如果项目准备冻结交付，**跳过 P2/P3 只做 P1+P4+P5+P6 是完全合理的收尾**。为「看起来模块化」做一次性大重写是这类项目最常见的自伤。

## 3. 行为契约：重构不许变的清单

把「不能变的事」写成编号清单，重构后逐条对照。按类归纳：

| 类别 | 具体项（示例） |
|---|---|
| 加载与命名空间 | script 顺序、eval 列表、`PT` 由谁创建、`module.exports` 位置 |
| 运行环境 | 引擎顶层无 DOM、单文件无外链、`file://` 可用 |
| 对外接口 | 退出码语义、报告字段名、人话行原文（被断言引用的） |
| 数据安全 | 源文件 sha256 不变、失败不留半份产物、`extra:true` 标记 |
| 语义取舍 | 填表不重画外观、压平拒绝 `NeedAppearances`、图片页抹字只报不做 |
| 交互 | 长任务可取消、默认值不变、面板名不变 |

每条都写成「**必须**……／**不许**……」，并注明它在哪个测试里被守住。没有测试守的契约，等于没有。

## 4. 交接文档结构

新对话要能只靠这一份文件开始工作：

```text
§0 给接手者的一段话（可直接复制进新对话）
§1 项目是什么 + 红线
§2 当前基线（数字 + 哈希 + 环境事实）
§3 目录与职责（含大文件的内部分块与行号）
§4 怎么跑、怎么验（命令 + 环境坑）
§5 重构路线 P0→P6
§6 行为契约 N 条
§7 最容易踩的坑（从开发手册里挑，不全量搬运）
§8 改动范围 → 最小验收集
§9 发布清单（可打勾）
§10 明确不做的事
§11 文档导航与「数字从哪来」
§12 待决策（留给用户拍板）
```

写作要求：

- **数字必须当场实测**，写进 §2 时注明来源文件。
- **§5 每条都要带「不做也可以」的判断**，否则接手者会觉得全都要做。
- **§10 比 §5 更重要**：不写清「不做什么」，新对话一定会「顺手修」。
- §0 那段话要包含：不要排新功能轮、先做 P0、红线是什么、交付格式是什么。

## 5. 三份文档的分工

| 文档 | 读者 | 内容 | 不要写 |
|---|---|---|---|
| 用户手册 | 使用者 | 功能、限制、示例 | 内部函数名 |
| 开发手册 | 维护者 | 模块 API、93 条坑、测试矩阵、变更表 | 营销话术 |
| 决策日志 | 未来的你 | 选型、差距表、每轮记录、取舍 | 逐行代码解释 |

**数字唯一来源**：回归报告 JSON、命令行报告 JSON、磁盘上的产物字节数。三份文档里的毫秒/字节都要能在这三处对上。

## 6. 发布清单

- [ ] 全量回归全绿，报告 `ok:true`，时间戳晚于最后一次代码改动。
- [ ] 命令行断言全过，`failed:[]`。
- [ ] 单文件重建；`file://` 双击能开；断网可用；`pt-inline=1`；无外链。
- [ ] 桌面版双击能开；只有一个文件形态能做到的能力（本机 OCR、Word COM）抽测一次，没环境就如实写「未测」。
- [ ] 命令行 `--help` 正常；`--dry-run` 不建目录。
- [ ] 文档数字与报告一致；冻结声明已写；「未完成事项」含明确延后的项。
- [ ] 交付物清单明确：哪些随包分发、哪些（测试、夹具、截图）不分发。

## 7. 收尾汇报格式

```text
改动点 / 借鉴来源（无则写无）/ 验证结果（带实测数字）/ 残留问题
现有功能 / 未完成事项 / 直接打开的网址
```

最后一行是用户真正会用的东西：一个能双击打开的绝对路径。别用「请运行 `python ...`」结尾。
