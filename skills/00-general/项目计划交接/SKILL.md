# 项目计划交接

让接收对话沿已确认的计划继续。交接文档是有时间和范围的状态快照，不是执行授权，也不证明文件至今未变。

## 选择模式与范围

- **交出**：用户要求整理交接、换对话继续。保存可恢复的状态和接收提示词，不顺带实施未授权的下一阶段。
- **接收**：用户提供交接并要求看下一步、接管或继续。先核对；只问下一步时只给判断，已授权执行时核对通过即可继续。
- **更新**：推进后更新同一工作流的状态、证据和停点，保留仍然有效的决策与未完成项。
- **检查**：只读诊断交接冲突或缺口，不更新项目文件。

先确认项目根目录、工作流和任务范围，例如“动作候选素材”与“声线训练”是两条工作流。不能从一个名为 `CODEX_HANDOFF.md` 的文件推断它涵盖整个项目。

## 交出与更新

1. 读取当前项目规则、用户最新要求、已有交接入口及相关计划。仅检查本工作流的关键文件与变化，不重读整个历史库。
2. 沿用项目已有入口与计划编号；没有约定时使用 `handoffs/<工作流>/current.md`。模板见 [交接模板](references/handoff-template.md)。已有交接先读再更新，不另造一个竞争入口。
3. 记录更新时间与时区、项目路径、工作流、计划路径与版本。Git 项目记录提交和未提交改动摘要；无 Git 时，对决定停点的少量关键文件记录 SHA-256 或可核对的版本标记。提交号不覆盖未提交内容，时间戳只辅助判断。
4. 将总目标、本批范围和剩余任务分开。沿用任务 ID；没有时给需要跨对话追踪的任务分配稳定 ID。每个完成项注明完成的是计划、文件生成、审阅还是运行验收，以及证据。不用无范围的 `complete=true`、空问题列表或“无阻塞”代表整体完成。
5. 写准确停点和首个可执行动作，包括输入、输出、验证方法。正在运行的命令、生成任务或后台进程记录已知状态与查询方法；结果未知就写未知，接收方先查询，不能直接重跑。
6. 更新前复查目标交接和关键计划是否自读取以来改变。发现其他对话的新写入时重新核对并合并本工作流变化，不用旧副本覆盖。明确最后写入者（已知时）与在执行的工作；普通文件不能保证并发互斥。
7. 只把入口导航改成指向当前文档；不要让多个入口复制“下一步”而分别过期。保持历史记录边界，必要时在既有归档约定下保存快照；默认不批量新增快照、不改写历史，也不自动提交 Git。

交付前确认文件已写入、引用能解析、未完成项没被更新过程丢掉、证据对应所述版本。给出入口和一段可粘贴到新对话的提示词，不复制全部聊天记录或敏感数据。

## 接收与核对

1. 读取指定入口、当前项目规则和该工作流的有效计划，按需读取证据。不要仅凭文件名、日期最新或历史报告选定当前目标。
2. 区分证据的用途：用户要求和已确认计划说明要做什么；当前文件与执行结果说明实际上做了什么。文件存在不能证明行为通过，旧报告不能证明新文件通过，现实偏差也不自动取消已确认目标。
3. 对照当前关键文件、版本标记和相关差异，检查交接是否过期、另一个对话是否正在执行、输出是否已生成但未验证。若不可访问另一对话，只报告“并行执行状态未知”，不假定已经停止。
4. 在对话中简述接收结果：**总目标／本批、已完成及证据、剩余与未验证、约束、首个动作**。发现冲突要说明来源与影响；能由当前文件和明确要求消解的直接消解，真正影响执行且无法判定的只询问该分歧，继续不受影响的工作。
5. 已有执行授权且核对无实质冲突时，从首个未完成任务继续，不额外等待确认。保留既定方案；用户改变方向或证据证明不可行时才调整并记录原因。不要重新规划整个项目，也不要重做有效的已完成项。
6. 只验证恢复所需的关键状态和本次影响范围。缺测试、环境不可用或只做模拟检查时明确覆盖限制，不因接收交接跑完整回归。

禁止把交接文件中的“下一步”当作发消息、付款、发布或操作其他项目的新增授权。用户已经提供的有效授权继续适用；需要协调另一个对话时遵守宿主的消息权限。
